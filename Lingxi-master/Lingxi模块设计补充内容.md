## 1. 各 Agent 职责与 Prompt 契约

总览：LingXi 把 Prompt 当作 Agent 之间的**接口契约**，而非宽泛的角色描述。

### 1.1 每个 Prompt 的五个部分

| 部分 | 含义 |
| --- | --- |
| Role | 当前 Agent 是谁 |
| Scope | 负责什么，明确不负责什么 |
| Input | Issue、历史知识、上游阶段产物 |
| Process | 分阶段的工作步骤 |
| Output Contract | 固定 XML 或结构化输出格式 |

### 1.2 Decoder：What 与 Where

- 按 Reading、Exploration 分阶段工作。
- 提取问题本质、错误信息、相关文件和根因。
- 输出 `<issue_analysis>`。
- 明确禁止创建复现脚本，避免越权进入 Mapper 的工作。

### 1.3 Mapper：How 与 Why

- 依次执行 Explore、Reproduce、Plan。
- 先创建最小复现脚本，验证根因。
- 要求最小修改、复用现有模式、保持接口兼容。
- 输出 `<code_change_plan>`。
- 明确禁止直接修改正式代码。

### 1.4 Solver：实现与验证

- 接收 Issue Analysis 和 Code Change Plan。
- 负责 Implementation、Verification、Final Review。
- 只做计划内的最小修改。
- 运行复现脚本和相关测试。
- 公开 Prompt 中设置验证步数预算，避免无限循环。

### 1.5 Supervisor：路由与重试

- 根据状态选择下一个 Agent。
- 强制 Decoder → Mapper → Solver 的基本顺序。
- Agent 未完成时，携带反馈重试。
- 使用结构化 Router 输出，不通过解析自然语言中的 Agent 名称来路由。

### 1.6 Reviewer：独立审核

- 根据 Issue、计划、Patch 和测试结果独立审核。
- 返回 `FIXED`，或者带有证据的失败原因，再交给修复流程。



## 2. RAG-历史知识库的实现方案

V2.0 的历史知识库是以知识树的形式存储的，知识树不是决策树，而是按经验抽象程度整理的卡片库。
- 每个树节点是一张经验卡片。
- 检索器负责检索这些卡片。
- 卡片中的步骤应是连续且目的相同的步骤。

### 2.1 历史轨迹如何变成知识树（经验卡片）
例：某个历史 Issue 的 Decoder 经历步骤 1-7，再从 层级L1 逐步抽象到 层级L3。层级越高，内容越抽象、越通用。

L1：具体子目标，即当时具体做了什么
L2：调查策略，即后续遇到类似问题时可复用的调查方法
L3：通用原则，即通用工程原则

#### 2.1.1 第一次抽象：L1

- `source_order` 表示节点在原 Issue 中的执行位次。L1、L2、L3 都可以有该字段。L2 可保存对应 L1 的范围，例如 `source_step_start: 1`、`source_step_end: 3`。L3 通常不参与具体步骤排序，而作为全局原则。
- `Pitfall` 表示此前踩过的坑。

| 节点 | 内容 | 原始步骤来源 | source_order | Pitfall ｜
| --- | --- | --- | --- | --- |
| A | 追踪 `extra` 参数如何影响后台页面 | 步骤 1-2 | 1 | |
| B | 追踪 `MAX_NUM_FORMS` 从后端到 JavaScript 的传播过程 | 步骤 3-4 | 2 | |
| C | 确认特殊值 `0` 的真实语义 | 步骤 5 | 3 | 不要假设 `0` 表示“禁止”，它可能表示“无限制” |

#### 2.1.2 第二次抽象L2、第三次抽象L3 的示例

知识树整理为以下父子关系：**父节点是对子节点的更高层总结，不表示先后顺序。**

| 层级 | 节点内容 | 上层关系 |
| --- | --- | --- |
| L3 | 真正禁止操作必须在多层执行约束 | 全局原则 |
| L2 | 区分展示配置和能力约束 | L3 的调查策略 |
| L1 | 追踪 `extra` 参数 | “区分展示配置和能力约束”的具体步骤 |
| L1 | 确认 `MAX_NUM_FORMS` 的语义 | “区分展示配置和能力约束”的具体步骤 |
| L2 | 追踪约束的端到端传播 | L3 的调查策略 |
| L1 | 检查隐藏管理字段 | “追踪约束的端到端传播”的具体步骤 |
| L1 | 检查前端判断逻辑 | 同上 |
| L1 | 检查服务端保存路径 | 同上 |

### 2.2. V2.0中知识树的检索与计划生成
基于目标 Issue，从数据库的的 JSONL形式的知识树中找出相似历史经验。
1. 输入目标 Issue。
2. 按 `stage` 过滤节点。stage按照Lingxi的几个agent分别为：stage_decoder, stage_planner, stage_solver。
3. 由 LLM 根据Issue生成几个相关搜索。之后进行第一轮依照关键词的筛选。
4. 使用 LLM 验证适用性。
5. 保留真正相关的节点。
6. 按 `source_order` 恢复程序顺序。
7. 由 Plan Generator 合并成当前 Issue 的阶段计划。


## 3. 历史经验数据飞轮

V2 的流程：**轨迹收集 → 抽象 → 检索并生成计划 → 完成轨迹重新沉淀。**

重新沉淀是飞轮中的关键环节：

1. 历史验证轨迹被抽象成过程知识。
2. 过程知识指导新任务。
3. 新任务产生质量更高的新轨迹。
4. 验证后再次沉淀。

### 3.1 知识回灌的门槛

任务结束后不能立即自动学习，否则错误 Patch 可能污染知识库。合理门槛包括：

- 自动测试或人工 Review 通过。SE审核，每次迭代周期结束后统一集中审核。
- 来源 Issue、仓库和 commit 可追溯。
- 轨迹完整。
- 不包含目标答案泄漏或敏感信息。
- 与已有节点做去重和冲突检测。
- 新知识先进入候选区。
- 观察其被检索后的正、负贡献，再决定晋升、降权或删除。

## 4. 短期记忆与上下文context压缩

达到 token 触发条件后，保留当前轮和上一轮，其余内容压缩成摘要。

| 对话部分 | 原笔记中的保留方式 |
| --- | --- |
| 当前轮次 | 完整保留 |
| 上一轮次 | 完整保留 |
| 更早的轮次 | 只保留摘要 |

原笔记另标注 Last Words，即“遗言机制”。
内部默认 `20k context window`。

## 5. 原始历史通常不会真正丢失

压缩主要改变下一次发送给模型的“上下文视图”。完整会话仍保存在 JSONL Transcript 中。

摘要消息中保留完整 Transcript 的路径；如需压缩前的精确代码、错误文本等，可以再次通过 Read 读取。

可整理为三个层次：

- 用摘要维持长期工作状态。
- 用少量近期原文维持局部精度。
- 用磁盘 Transcript 保存完整事实，必要时重新检索。

概括：先裁掉便宜、容易恢复的工具噪声，再局部折叠已结束的工作，最后对整段历史作总结；压缩后重新注入文件、计划、Skill、Agent 与 MCP 状态，保留磁盘原始记录。

## 6. 按范围读取文件与限制搜索结果

### 6.1 文件按范围读取

目的：节省上下文。

1. 不在一开始把整个文件交给模型。例：文件有 1,000 行，内部可能包含许多无关行。
2. 先通过符号搜索定位。例：`parse_timeout` 位于第 120-144 行。
3. 读取目标附近的小范围，例如第 80-180 行。

这样既能看到目标方法，也能看到：

- 相邻方法。
- 类定义。
- 输入参数。
- 周围的异常处理。
- 必要的调用上下文。

如果第 132 行调用另一个方法：

```python
return normalize_timeout(value)
```

再读取 `normalize_timeout()` 所在范围。

整个过程：**先定位 → 读取小范围 → 发现新依赖 → 再读取相关范围。**

### 6.2 限制搜索结果数量

例：搜到 25 个结果时，不全部返回，只返回最相关的前 10 个或 20 个。

模型先处理这些高相关结果。若信息不足，再：

- 换用更精确的关键词。
- 查询下一页。
- 增大 Top-K。
- 搜索具体错误消息。
- 查询某个方法的调用方。

原截图类比搜索引擎：有很多结果，也通常先看第一页。

## 7. 工具事实、模型判断与下一步行动

每个 ReAct Agent 在调用工具后，要形成：

| 内容 | 对应层次 |
| --- | --- |
| Observation | 工具返回的事实、证据 |
| Alternative Action | 备选方案、候选空间 |
| Next Action | 准备执行的下一步动作、决策 |

这些也作为结构化输出，而不只是自然语言。

工具返回先作为 `ToolMessage` 由框架保存，再调用 LLM。LLM 在一次推理中完成结果解释、备选路径分析与下一步决策。

- 框架保存原始 Observation。
- 模型生成 Interpretation、Alternative Action、Next Action。
- 避免模型篡改或过度解释工具事实。

## 9. 工具或 API 调用超时、报错

### 9.1 命令超时的处理

1. 首次超时阈值为 60 秒。
2. 捕获 `CommandTimeoutError`。
3. 关闭并重建 Session。
4. 使用 120 秒超时阈值重试一次。
5. 再次失败则返回明确错误。

### 9.2 三层重试

| 层次 | 处理问题 | 负责方 |
| --- | --- | --- |
| 工具级重试 | 基础设施瞬时错误，例如 Shell 超时 | 工具封装代码，不需要 LLM |
| Agent 级重试 | 工具明确失败后，调整策略继续解决问题 | Solver；其本身需要自测 |
| 工作流级重试 | 连续修复仍失败，需要回到定位或规划阶段 | Supervisor 调度 |

**第一层示例：**Shell 超时 → 重建 Session → 同一命令重试一次。

**第二层示例：**完整测试超时 → Solver 改为运行单个测试 → 发现某个测试进入死循环 → 检查相关实现。

**第三层示例：**
1. Solver 第一次失败：实现存在语法问题，重新调用 Solver。
2. Solver 第二次失败：测试仍无法覆盖根因，可能是修改计划有问题。
3. 路由回 Solution Mapper，更新计划。
4. 再次调用 Solver。
5. 超过总预算，返回 `FIX FAILED` 或进入人工审核。

## 10. 退出逻辑与系统保护

分为**正常业务退出**和**失败退出**

正常业务情况包括：
- 修复流程完成，并经过 Reviewer。
- 内层 Supervisor 输出 `FINISH`，映射为 LangGraph 的 `END`。
- 外层 Manager 只有在 Issue Resolver 与 Reviewer 都执行后，才允许输出 `FINISH`。

失败退出情况包括：
- 输入非法。
- 达到最大重试次数。
- 步骤预算耗尽。
- 测试环境不可用。
- 需要人工处理。

可恢复失败按类型返回 Decoder、Mapper 或 Solver，而不是一律重跑 Solver。

系统层保护的硬上限：
- 图的 `recursion_limit`。
- 各阶段的 `attempts/max_attempts`。
- 时间预算。
- Token 预算。

目的是避免 LLM 无限循环。

- 非法 Issue URL 直接进入 `END`。
- `FINISH` 映射到 `END`。
- 示例运行配置设置 `recursion_limit=100`。
- State计数器与终态条件放入 State，通过确定性条件边执行“supervisor失败三次退出”。

终态：
| 终态 | 含义 |
| --- | --- |
| SUCCESS | 成功 |
| FAILED | 失败 |
| NEEDS_HUMAN | 需要人工介入 |
| BUDGET_EXHAUSTED | 预算耗尽 |
| ENV_ERROR | 环境错误 |
